Software Development Life Cycle
SDLC is a structured process for planning, creating, testing, and deploying software. It provides a clear framework that guides development teams through each phase systematically.
Key Definition
SDLC defines the phases of software development, ensuring quality, predictability, and efficient use of resources.
PHASE 1
Planning
Feasibility study, resource allocation, project scope, timeline estimation.
PHASE 2
Requirements
Gather functional & non-functional requirements, stakeholder interviews, SRS document.
PHASE 3
Design
Architecture design, database schema, UI/UX wireframes, technical specifications.
PHASE 4
Implementation
Actual coding, code reviews, version control, development best practices.
PHASE 5
Testing
Unit, integration, system, acceptance testing. Bug tracking and regression testing.
PHASE 6
Deployment & Maintenance
Production release, monitoring, patches, user support, and iterative improvements.
Requirements Engineering
Requirements define what a system should do. The requirements engineering process ensures all stakeholder needs are captured, validated, and documented before development begins.
Functional Requirements
Describe what the system should do.
• User login and authentication
• Search and filter products
• Generate reports
• Send email notifications
Non-Functional Requirements
Describe how well the system performs.
• Performance: load <2s
• Security: encrypted data
• Scalability: 10k concurrent users
• Availability: 99.9% uptime
User Story Format
"As a [role], I want [feature] so that [benefit]"

Example: "As a customer, I want to track my order so that I know when to expect delivery."
System Design Principles
System design bridges requirements and implementation. Good design leads to maintainable, scalable, and robust software systems.
DRY
Don't Repeat Yourself
Every piece of knowledge should have a single, unambiguous, authoritative representation in the system.
KISS
Keep It Simple, Stupid
Simplicity should be a key goal in design. Avoid unnecessary complexity.
YAGNI
You Aren't Gonna Need It
Don't add functionality until it is necessary. Avoid over-engineering.
SoC
Separation of Concerns
Divide a program into distinct sections, each addressing a separate concern (UI, business logic, data).
SOLID Principles
Five design principles that make software designs more understandable, flexible, and maintainable. Essential for object-oriented programming.
S
Single Responsibility Principle
A class should have only one reason to change. Each class handles one specific concern.
O
Open/Closed Principle
Software should be open for extension but closed for modification. Add new features without changing existing code.
L
Liskov Substitution Principle
Subtypes must be substitutable for their base types. Derived classes should extend base classes without breaking functionality.
I
Interface Segregation Principle
Clients should not be forced to depend on interfaces they don't use. Create specific interfaces rather than one general-purpose one.
D
Dependency Inversion Principle
High-level modules should not depend on low-level modules. Both should depend on abstractions.
Design Patterns
Reusable solutions to commonly occurring problems in software design. Categorised into Creational, Structural, and Behavioural patterns.
Creational
• Singleton
• Factory Method
• Abstract Factory
• Builder
• Prototype
Structural
• Adapter
• Bridge
• Composite
• Decorator
• Facade
Behavioural
• Observer
• Strategy
• Command
• Iterator
• State
Singleton Example
class Database {
  static instance = null;
  static getInstance() {
    if (!this.instance) this.instance = new Database();
    return this.instance;
  }
}

Methodology Comparison
🌊 Waterfall
Sequential, linear process. Each phase must be completed before the next begins. Best for well-defined, stable requirements.
Pros
  • Clear structure
  • Easy to manage
  • Well documented
    • Cons
  • Inflexible to change
  • Late testing
  • High risk
    • 🔁 Agile / Scrum
    Iterative, incremental delivery in sprints (2–4 weeks). Embraces change. Customer collaboration throughout.
    Pros
  • Flexible & adaptive
  • Early delivery
  • Customer feedback
    • Cons
  • Less predictable
  • Needs engagement
  • Scope creep risk
    • 🌀 Spiral
    Combines iterative development with systematic risk analysis. Each cycle involves planning, risk analysis, engineering, and evaluation.
    Pros
  • Risk management
  • Customer feedback
  • Iterative
    • Cons
  • Expensive
  • Complex to manage
  • Needs risk expertise

    function shoppingCart() {
      let items = [];
      return {
        add: (item) => items.push(item),
        remove: (id) => {
          items = items.filter(i => i.id !== id);
        },
        getTotal: () => items.reduce((s,i) => s + i.price * i.qty, 0),
        count: () => items.length,
        clear: () => { items = []; }
      };
    }
    Testing Strategies
    Unit Testing
    Test individual functions in isolation. Mock dependencies. Fast and targeted.
    Integration Testing
    Test how modules interact. Check data flows between components correctly.
    TDD (Test-Driven Dev)
    Red → Green → Refactor. Write failing test first, then write code to pass it.
